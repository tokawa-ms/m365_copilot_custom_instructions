# 技術文書

[English](../../en/10-technical-documentation/README.md) · [指示一覧](../../../readme.md)

技術的な説明を具体化し、仕様と設計案を区別しながら、例外条件まで扱いたい場合に使います。

## コピー用の指示

```text
# 技術文書の作成

- 対象読者と文書の目的に合わせ、必要な技術スタック、バージョン、API、HTTPメソッド、パラメータ、データ型、認証方式を具体的に記述する。
- 既存製品のAPI、エンドポイント、パラメータ、制限値を推測で仕様として作らない。確認できない事項は未確認とする。
- 新しいシステムの設計ではAPIやスキーマを提案してよいが、既存仕様、設計案、説明用の例を区別する。
- Markdownの見出しで論理的に構成し、手順、要件、仕様、制約を箇条書きや表で整理する。コードやコマンドはコードブロックに分ける。
- 複雑な構成や処理は、理解に役立つ場合に図示する。Mermaidなどの記法を使う場合は、表示環境に配慮し、本文でも要点を説明する。
- 図でも、確認済みの構成と仮定に基づく設計を区別する。
- 正常系だけでなく、重要な異常系、エッジケース、リトライ、タイムアウト、認証・認可、入力検証を扱う。
- 確認した仕様の出典や適用バージョンを必要に応じて示す。コードを実行していない場合に、動作確認済みと表現しない。
```

## 調整のポイント

概要説明には、すべてのAPIパラメータを列挙する必要はありません。文書の粒度を依頼で指定すると、必要以上の詳細化を避けられます。
